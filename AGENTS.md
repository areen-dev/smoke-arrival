## 2. The problem

Every October, farmers in Punjab and Haryana burn paddy residue. Delhi
sits 250–400 km downwind and breathes it. Existing tools — CPCB, SAFAR,
AQI apps — report air quality **after** the smoke has arrived. They
measure; they do not forecast.

Nobody can tell a school, a parent, or someone with asthma: *"smoke
reaches your area at 7pm tomorrow, for a four-hour window."*

**Our single claim:** we forecast the arrival time and the path of
smoke, from public satellite fire data plus forecast wind.

## 3. Architecture

```
NASA FIRMS CSVs (4 sensors)  ──► merge, de-duplicate, snap to 0.25° cells
   public, no API key                                  │
                                                       ▼
Open-Meteo hourly wind ──► u/v components ──► Lagrangian advection
   public, no API key                          (1 h steps, 48 h horizon)
                                                       │
                        arrival = first step inside the city radius
                        (fires already inside the city are "local",
                         never credited as transported smoke)
                                                       │
                        ▼
        0–100 smoke-load index + first-arrival time + per-source path
                                                       │
                        ▼
             FastAPI  ──►  JSON API  +  one HTML map page
                                                       │
                        ▼
              AWS Lambda + Function URL (ap-south-1)
```

Deliberate simplifications, with reasons:

- **Lagrangian drift, not a dispersion model.** Carrying a blob of
  smoke along the wind is the simplest thing that answers "when". A
  real plume model needs emission inventories and mixing-height data
  we do not have, and cannot be validated in three days.
- **One Lambda, not a full deployment.** No servers to babysit, no
  containers, no networking. The same FastAPI app runs on a laptop and
  on Lambda through Mangum, so nothing is rewritten for the cloud.
- **No database.** FIRMS updates a few times a day, so one request can
  compute the answer. The API caches for 15 minutes.
- **One static HTML file, Leaflet vendored into the repo.** No build
  step, no npm, no CDN dependency for the map library.

## 4. Tech stack

| Piece | What it is | Why this |
|---|---|---|
| Python 3.13 | the language | matches the Lambda runtime, long support window |
| FastAPI | web framework for the API | team is learning it; free input validation and browsable docs |
| Mangum | adapter turning a FastAPI app into a Lambda handler | the reason nothing is rewritten for AWS |
| httpx | async HTTP client | four FIRMS files download together, not one by one |
| numpy | array maths | the wind grid is a 3-D array; pure Python loops are slow and error-prone |
| pytest | test runner | the only way to know the maths is right when live data is quiet |
| uv | environment + dependency management | fast, and it can build a Lambda bundle for the right platform |
| Leaflet 1.9.4 | map library, **vendored**, not from a CDN | removes a live external dependency from the judged moment |
| HTML/CSS/vanilla JS | the page | no build step, nothing to break at 2am |
| AWS Lambda + Function URL | serverless hosting, region `ap-south-1` | smallest thing that satisfies "deployed on AWS" |
| AWS CLI | deploy and logs | two commands; less to learn than SAM or CloudFormation |
| CloudWatch | logs, automatic with Lambda | zero-setup proof on camera that it really runs |
| Git + GitHub | version control, public repo | the rules require a public repo, and history is evidence |

**Not in the stack, and why:** S3 and CloudFront (one Lambda serves the
page itself), DynamoDB (nothing to store), SNS/EventBridge (alerts need
real subscribers to mean anything), SAM (only used in the fallback
path), Docker, containers, React, Vite, any database.

## 11. The model specification

Implement exactly this. Units matter.

**Constants** (all in `app/config.py`, commented):

```
dt_seconds            3600
max_forecast_hours    48
decay_length_km       300.0
index_half_point      4000.0
min_travel_km         50.0
cell_deg              0.25
wind height           10 m
```

**Cities** (key, name, lat, lon, radius_km): delhi 28.6139 77.2090 45 ·
gurugram 28.4595 77.0266 20 · noida 28.5355 77.3910 20 · chandigarh
30.7333 76.7794 25 · ludhiana 30.9010 75.8573 25 · amritsar 31.6340
74.8723 25 · jaipur 26.9124 75.7873 30 · lucknow 26.8467 80.9462 30

**Wind direction convention:** meteorological direction is where the
wind blows **from**. So `u = -speed * sin(rad)`, `v = -speed * cos(rad)`.

**Step:** `dlat = v * dt / 111320`, `dlon = u * dt / (111320 * cos(radians(lat)))`.

**Distance:** haversine, R = 6371.0088 km.

**Sampling:** bilinear in space, linear in time.

**Arrival:** the first hour a particle comes within the city's radius.

**The local-fire rule:** if a source cell is already inside the city's
radius, it is burning **there**. Count it separately as
`local_fire_cells` and never as an arrival. Without this, a field fire
inside the city reports "smoke arrives in +1 hour", which is wrong and
is the first thing a judge will poke at.

**Minimum travel:** an arrival only counts if the particle travelled at
least `min_travel_km` (50 km).

**Score:** per arriving source,
`contribution = cell_frp * exp(-travel_km / decay_length_km)`.
Then `index = 100 * total / (total + index_half_point)`, which
saturates at 100.

**Bands:** `>= 70` severe · `>= 40` high · `>= 15` moderate ·
`> 0` low · else clear.

**Explain:** one plain sentence per city, in three cases — something is
arriving; only local burning; nothing arriving and here is the nearest
fire.

## 12. Known traps — already paid for, do not rediscover

1. **A fire inside the city is not transported smoke.** See section 11.
2. **A quiet forecast is a correct forecast.** The model will often
   report nothing arriving, because the wind is not carrying smoke that
   day. That is physically right. **Never tune the model to make it
   produce alarms for the demo.** Report the calm case and explain it.
3. **Test the model, not the output.** When nothing is arriving, a
   broken model and a correct one look identical on screen. Tests are
   the only way to tell.
4. **Build the Lambda bundle for Lambda's platform.** Use
   `--python-platform x86_64-manylinux2014`. Without it you ship
   host-built `.so` files that Lambda cannot load.
5. **Do not test the bundle with your host Python.** A cp313 bundle
   must be imported by Python 3.13 (`uv run --python 3.13`), not by a
   newer interpreter, or you get a confusing `pydantic_core` error.
6. **A hand-written Lambda test event needs
   `requestContext.http.sourceIp`**, or Mangum raises `KeyError`. For
   local testing just use `uvicorn`.
7. **Leaflet needs its marker images**, not just the stylesheet. Keep
   all five images in `static/vendor/leaflet/images/`.
8. **Do not link Leaflet from a CDN.** It is vendored on purpose so
   that the judged moment does not depend on a third party being up.
9. **Compute on demand, not on a schedule.** Generate the forecast on
   request with a 15-minute cache. No cron, no queue, no database.
10. **Cache the last good forecast, and serve it if a live fetch fails.**
    The FIRMS and Open-Meteo calls happen at the moment a judge opens the
    page. Save the last successful payload to a file, and fall back to it
    rather than showing an error. The page then always shows real data,
    even if the data source is having a bad day. Leaflet is already
    vendored so that risk is gone; this covers the data.
    Not fixable the same way: the CARTO map tiles, which are millions of
    individual images. If CARTO is down the map background goes blank, but
    the fire circles, forecast lines and city list still render, because
    those come from our own code.
